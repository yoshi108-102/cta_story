Probe Playbook

Probe を根にした分岐設計

今回の目的は、Seed の種類ごとの分岐ではなく、 各 Probe ごとにどんな深掘り分岐が存在するか を可視化すること。 Seed は入口の違いとして残しつつ、深掘り本体は Probe を根にした playbook として持つ。 React Flow では、この playbook を木として表示することを想定する。

Probe-first React Flow 向きの tree 共通分岐 + probe 固有の質問例

前提整理

深掘りの本体を決めるのは SeedType ではなく Probe である。Question / Idea / Anomaly の違いは入口の違いに近く、 一度掘り始めたら、工程・材料・身体などの共通 Probe でかなり同じように扱える。

SeedType

何から始まったか。問い、思いつき、違和感の違い。

Probe

何について掘るか。工程、材料、身体、環境などの観点。

Branch

その Probe で次に何を確かめるか。特定、差分、変化、判断基準など。

共通の分岐テンプレ

各 Probe に対して、まずは次の 6 分岐を共通テンプレとして持つのがよい。 これは質問文の違いではなく、何の操作をかけるか の違いである。

1. 特定

何のことか、どの場面か、どの対象かを固定する。

2. 差分

いつもと何が違うか、予想と何が違うかを見る。

3. 変化

前後でどう変わったか、途中で切り替わったかを見る。

4. 判断基準

何を見て OK / NG / 危険 と見ていたかを掘る。

5. 影響

その要因が結果や次の操作にどう効いたかを見る。

6. 移送

problem、mismatch、別 Probe への次遷移を決める。

React Flow に載せる最小形

1

Probe Root

例: 工程 / タイミング, 材料, 身体 / 操作。

2

共通 Branch

特定, 差分, 変化, 判断基準, 影響, 移送 を 1 層目に置く。

3

質問例 / 取得したい情報

各 branch の下に、具体的な質問例や観察対象を leaf として置く。

最初は DAG や表より、 Probe ごとの独立した tree として見せる方が実装も理解も単純である。

例 1: 工程 / タイミング Probe

工程 / タイミング

どの処理の時だったか、どの順番だったか、どの切り替わり点だったかを掘る

Root

工程 / タイミング

特定

  • どの工程の時だったか
  • 前後どの作業の間だったか
  • 開始直後か、終盤か、切り返し前後か

差分

  • いつもの順番と何が違ったか
  • 予想していたタイミングとの差は何か
  • 本来ここで起きるはずのことは何か

変化

  • どの瞬間で様子が変わったか
  • 途中で手順を変えたか
  • どこが境目だったか

判断基準

  • 次の工程へ進めると何で判断したか
  • まだ早い / 遅いを何で見ていたか
  • タイミングの良し悪しを何で見ていたか

影響

  • そのタイミングの違いで何が起きたか
  • 後続工程にどう影響したか
  • その時点で戻せたのか、戻せなかったのか

移送

  • 手順理解の problem へ進む
  • 工程間のズレとして mismatch へ進む
  • 別 Probe として材料や身体へ移る

例 2: 材料 Probe

材料

対象の材質、状態、個体差、条件差がどう効いたかを掘る

Root

材料

特定

  • 何の材料だったか
  • 材質、太さ、状態はどうだったか
  • いつも使うものと同じだったか

差分

  • いつもの材料と何が違ったか
  • 予想していた材料特性との差は何か
  • 個体差はあったか

変化

  • 途中で状態は変わったか
  • 温度や湿り気で変化したか
  • 作業中に抵抗感や見え方が変わったか

判断基準

  • その材料状態を何で見分けたか
  • 良い / 危ないを何で判断したか
  • 触感、見た目、音などの手がかりは何か

影響

  • 材料差が結果にどう効いたか
  • 操作の仕方を変える必要があったか
  • 別の手順や道具選択に影響したか

移送

  • 材料理解の problem へ進む
  • 材料差の説明不能点を mismatch にする
  • 身体 / 道具 Probe へ横移動する

例 3: 身体 / 操作 Probe

身体 / 操作

姿勢、力加減、手順、感覚、操作の切り替えを掘る

Root

身体 / 操作

特定

  • どの姿勢、どの持ち方、どの手順だったか
  • どの動作をしていた瞬間か
  • どの部位に意識を置いていたか

差分

  • いつもの動かし方と何が違ったか
  • 予想した手応えとの差は何か
  • 思っていた力加減との差は何か

変化

  • 途中で力の入り方は変わったか
  • どこで手の使い方を変えたか
  • 身体感覚が切り替わった瞬間はどこか

判断基準

  • うまくできている感覚を何で見ていたか
  • 危ないと感じる手応えは何か
  • 次に進める身体感覚の基準は何か

影響

  • その操作差で結果はどう変わったか
  • 他の工程や道具選択に影響したか
  • やり直しや補正が必要になったか

移送

  • 操作理解の problem へ進む
  • 手応えの説明不能点を mismatch にする
  • 材料 / 工程 Probe へ横移動する

表にするより tree にする理由

1. 次の聞き先が見える

表は一覧には強いが、「次に何を聞くか」を持ちにくい。

2. React Flow と相性がよい

既存実装は tree layout が前提なので、まず木として整理する方が素直。

3. playbook として使いやすい

人が辿るにも、AI が follow-up を出すにも tree の方が扱いやすい。

一覧性が必要になった段階で、 後から Probe × Branch の表に変換するのは簡単だが、 逆はやや難しい。

実装に落とすときの最小単位

レベル React Flow 上の役割 持つ情報
Probe Root 木の親 Probe 名、説明、適用対象
Branch Node 共通分岐 特定 / 差分 / 変化 / 判断基準 / 影響 / 移送
Leaf Node 具体質問例 質問文、狙い、次に渡す先
