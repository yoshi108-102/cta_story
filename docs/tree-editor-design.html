なぜなぜ問答 樹形図エディタ設計書

対象は「丸棒矯正」のなぜなぜ問答。公開用の樹形図を作れることが目的で、コードは使い捨て前提。 そのため、可視化の派手さよりも、深い階層でも読みやすく、状態管理が単純で、後から壊しにくい構成を優先する。

前提: AI 機能なし 公開: Firebase Hosting 優先 編集: ノード追加 / エッジ追加のみ 方針: React Flow は不採用

1. 結論

採用案

フォーカス型アウトラインエディタ を採用する。 左に折りたたみ可能なツリー一覧、中央に選択ノードの詳細と直下の子、右に追加フォームを置く。 全体を常時描画しない。

採用理由

深い階層でも崩れにくく、Canvas 系ライブラリより編集フローが明快。さらに、状態は nodes[] の単純な配列で管理できる。

今回あえて捨てるもの

ノードをドラッグして線を引くような「グラフ編集らしさ」は捨てる。なぜなぜ問答では、見やすさと壊れにくさの方が価値が高い。

2. 目的と非目的

目的

  • 深い階層でも見失いにくい UI にする
  • ノード追加とエッジ追加だけで運用できる
  • 使い捨てコードとして把握しやすい実装にする
  • 樹形図の状態を単純な JSON として保持する
  • 公開側と編集側を分けつつ、構成を重くしない

非目的

  • 巨大グラフを高速にパン・ズームすること
  • 複数人の同時編集
  • ドラッグ配線や自由配置
  • リッチテキストや Markdown 編集
  • 複雑なアクセス制御や監査ログ

3. UI 候補比較

候補 見え方 編集しやすさ 実装複雑性 判断
React Flow 系の自由配置グラフ 派手だが、深い木では視線移動が大きい ドラッグはできるが、なぜなぜ問答には過剰 高い 不採用
D3 tidy tree / vis-network hierarchical / Cytoscape breadthfirst 自動整列はできるが、深い階層では横幅か縦幅に寄りやすい 閲覧向きで、編集 UI を別で作る必要がある 中〜高 不採用
DOM ベースのアウトラインツリー + フォーカス詳細 全体を無理に出さず、今見る枝に集中できる 追加操作をボタンとフォームに寄せられる 低い 採用

React Flow を外す理由

ノード位置という余計な状態が増える。見た目の自由度は高いが、深い木で「どこを読めばよいか」が改善しない。

自動レイアウト系を外す理由

可視化自体は可能でも、編集は別 UI になる。結果的に状態管理とレイアウト調整が二重化しやすい。

採用案の特徴

木構造を「全体図」ではなく「現在の文脈」として見せる。読みやすさを UI 構造で担保する。

4. 採用 UI

UI は 3 ペイン構成にする。ただし右ペインはモーダルに落としてもよい。要点は「ツリー一覧」「選択ノードの文脈」「追加操作」を分けること。

この UI の利点

  • 今読むべきノードと、その前後関係が分かりやすい
  • 全体図の横長化を避けられる
  • ツリー編集を通常のフォーム処理として実装できる

グラフィカル追加を切る理由

  • ドラッグ配線は誤操作や例外処理が増える
  • タッチ操作や狭い画面で破綻しやすい
  • 木構造なのに、自由グラフの UI を持ち込む意味が薄い

5. 状態モデル

樹形図は 単一 JSON ドキュメント として保存する。ノードごとの Firestore サブコレクションにはしない。 使い捨てコードで複雑性を落とすなら、まずは 1 ドキュメント管理が適切。 

{
  "treeId": "marubou-001",
  "title": "丸棒矯正 なぜなぜ問答",
  "rootNodeId": "n-root",
  "nodes": [
    {
      "id": "n-root",
      "parentId": null,
      "kind": "problem",
      "label": "矯正後の丸棒で真直度 NG が発生した",
      "note": "起点ノード",
      "createdAt": "2026-03-09T10:00:00Z"
    },
    {
      "id": "n-101",
      "parentId": "n-root",
      "kind": "why",
      "label": "入側材の曲がり把握が不足していた",
      "note": "",
      "createdAt": "2026-03-09T10:05:00Z"
    },
    {
      "id": "n-102",
      "parentId": null,
      "kind": "why",
      "label": "未接続ノードの例",
      "note": "",
      "createdAt": "2026-03-09T10:06:00Z"
    }
  ]
}

なぜ parentId だけで持つのか

  • エッジを別管理しなくてよい
  • childIds と二重管理にならない
  • ノード追加は配列に 1 件足すだけ
  • エッジ追加は対象ノードの parentId を更新するだけ

ローカル UI 状態

{
  selectedNodeId: "n-101",
  expandedNodeIds: ["n-root", "n-101"],
  draftLabel: "",
  draftNote: "",
  attachTargetId: null
}

子一覧は毎回 nodes.filter(node => node.parentId === selectedNodeId) で求めてよい。小規模前提ならこれで十分で、余計なインデックスを持たない方が壊れにくい。

6. 編集操作

操作 1: ノード追加

  1. 親ノードを選択する
  2. ラベルと注記を入力する
  3. 保存時に新規ノードを nodes[] へ追加する
  4. 新規ノードの parentId は選択中ノード ID とする

操作 2: エッジ追加

  1. 親ノードを選択する
  2. 未接続ノード一覧から接続先を選ぶ
  3. 接続時に対象ノードの parentId を更新する
  4. すでに parentId があるノードは一覧に出さない

保存単位

変更があるたびにツリー全体を保存してよい。差分保存は不要。

循環防止

親にしようとしているノードが、自分の子孫でないことだけ確認する。

表示順

兄弟ノードの順番は createdAt 昇順で十分。並び替え機能は入れない。

7. Firebase 構成

この要件なら Firebase App Hosting より Firebase Hosting の方が自然。 SSR もサーバー API も不要なので、React の SPA を Hosting に置き、Auth と Firestore をクライアント SDK で使う方が単純。

デプロイ Firebase Hosting を推奨。App Hosting は不要。もし App Hosting に統一したいなら、同じ SPA を載せるだけにして server 機能は使わない。
認証 Firebase Auth の Google ログイン。編集者だけ許可する。
保存先 Firestore の 2 ドキュメント構成。draft と published を分ける。
読み込み 公開ページは published を読む。管理画面は draft を読む。
公開操作 管理画面の「公開」で draft の内容を published に上書きする。 
/trees/{treeId}/versions/draft
/trees/{treeId}/versions/published

この構成の利点

  • サーバーコードがいらない
  • 公開版と編集中を混ぜずに済む
  • JSON の全保存だけで完結する

後から困る可能性

  • ノード数が大きくなると 1 ドキュメント上限に近づく
  • 同時編集には向かない
  • 細かい監査ログは残しにくい

8. 最低限の耐性

最低限やること

  • 入力は plain text のみ
  • HTML や Markdown を保存しない
  • React で通常描画し、dangerouslySetInnerHTML を使わない
  • Firestore Rules で編集権限を絞る
  • AI を使わないので Generative Language API は無効にする

今回は不要

  • WYSIWYG エディタ
  • HTML sanitizer
  • グラフ描画用 Canvas ライブラリ
  • サーバー側の複雑な検証 API
match /trees/{treeId}/versions/published {
  allow read: if true;
  allow write: if false;
}

match /trees/{treeId}/versions/draft {
  allow read, write: if request.auth != null
    && request.auth.token.editor == true;
}

Firebase の Web 用 apiKey 自体は秘密鍵ではないが、AI を使わない前提ならそれで問題化しにくい。 気にすべきなのは、不要な API を有効にしないことと、編集権限を Firestore Rules で閉じること。

9. 実装順序

  1. React SPA を作る。UI は左ツリー + 中央詳細 + 追加フォームの 2〜3 ペインにする。
  2. TreeDraft 型と nodes[] の単一状態を作る。
  3. ノード追加を実装する。
  4. 未接続ノードを親へつなぐエッジ追加を実装する。
  5. Firestore の draft 保存を実装する。
  6. 公開用の published コピーを実装する。
  7. 最後に公開ページを作る。公開側は編集 UI を持たせない。

最初の 1 版では、ノード削除、並び替え、ドラッグ、検索、ミニマップを入れない方がよい。 これらはすべて状態モデルを複雑にし、使い捨てコードの寿命を縮める。
