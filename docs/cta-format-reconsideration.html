再考メモ

CTAフォーマット再考

現行の problem / why / factor は「なぜなぜ分析」には使えるが、ACTA/CTAの本来目的 (認知的難所、判断手掛かり、熟練者戦略、初心者エラー) を保持できていない。
本メモでは、樹形UIを活かしつつCTAフォーマットへ寄せるための採用案を定義する。

対象: cta_story 作成日: 2026-03-09 ステータス: 提案

1. まず何がズレているか

現行モデルの強み

  • 木構造としては単純で編集が容易
  • 因果を下方向に掘る読み方が明快
  • 最小UIで運用できる

CTA観点での不足

  • 「なぜ」以外の認知知識を記録できない
  • 手掛かり(cue)と戦略(strategy)が混在する
  • 初心者エラーを独立して扱えない
  • Task DiagramとCognitive Demands Tableへの接続が弱い

判定: 現行は「原因分析ツリー」としては有効だが、「CTA知識ベース」としては情報軸が不足。

2. CTAとして最低限必要な情報軸

軸 意味 現行対応 必要アクション
Task Step 作業工程の文脈 曖昧 ノード種別または属性として明示
Cognitive Demand どこが難しいか 一部whyに埋没 独立ノード化
Cue / Signal 何を見て判断したか noteに混在 独立ノード化
Expert Strategy 熟練者の打ち手・着眼 noteに混在 独立ノード化
Novice Error 初学者の典型的ミス 未定義 独立ノード化

3. フォーマット候補の比較

案A: 現行拡張

problem/why/factorを維持し、note規約だけ追加

実装は最小だが、入力品質が人依存になり、CTA再利用性が上がりにくい。

案B: 表形式中心

Cognitive Demands Tableを主にして木構造を補助化

CTA忠実度は高いが、現行UI/コードとの乖離が大きく改修コストが高い。

案C: ハイブリッド

木構造を維持しつつノード種別をCTA軸に再定義

現行との連続性を保ちながら、CTA情報を構造化して持てる。
採用推奨: 案C (ハイブリッド)

4. 採用推奨フォーマット (案C)

4-1. ノード種別

type NodeKind =
  | "task_step"
  | "cognitive_demand"
  | "cue_signal"
  | "expert_strategy"
  | "novice_error";

4-2. 関係ルール (最小)

  • root は task_step または分析テーマノード
  • task_step の子に cognitive_demand を置く
  • cognitive_demand の子に cue_signal / expert_strategy / novice_error を置く
  • 全ノードは単一親を維持 (木構造を維持)

5. UIへの落とし込み

ツリー側で見せるもの

  • ノード種別バッジをCTA語彙へ差し替え
  • 選択経路の強調は現行仕様を踏襲
  • 子ノード件数を「関連知識数」として表示

詳細側で見せるもの

  • 選択ノードのCTAカテゴリ説明
  • 親子の意味関係 (Step → Demand → Cue/Strategy/Error)
  • 将来のTable出力用キー (source/interviewRef など) を追加余地として保持

6. 移行方針 (現行データから)

  1. problem は暫定で task_step に変換する
  2. why は暫定で cognitive_demand に変換する
  3. factor は暫定で cue_signal に変換し、必要に応じて手動修正する
  4. 編集UIにノード種別説明を表示し、再分類の判断を支援する
旧データは意味が混在しているため、100%自動変換は不可。初回は運用者レビュー前提で進める。

7. 再考の結論

いまの実装資産 (木構造UI・編集フロー) を活かすには、構造は維持して語彙をCTA化するのが最適。 先にノード種別と関係ルールを差し替え、その後にCognitive Demands Table出力を追加する順が安全。

次の実装フェーズは、NodeKind の再定義、既存フォーム選択肢の更新、seedデータの置換、表示ラベル更新の4点を最小セットとする。
