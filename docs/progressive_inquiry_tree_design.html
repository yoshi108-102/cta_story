Design Spec

Progressive Inquiry Tree 設計書

目的は、Problem -> Working Theory -> Gap/Contrast を曖昧な1本鎖として持つのではなく、 文献に沿って theory-local な gap と theory-between な contrast を分離した設計へ落とすこと。 既存の tree editor が単一親の木構造であることを前提に、無理なく導入できる形を採る。

対象プロダクト: cta_story 作成日: 2026-03-10 前提: 現行 tree editor は単一親ツリー 関連サーベイ: focused survey

1. 設計判断の要約

採用

gap は working_theory の子ノードとして持つ。 名前は mismatch に寄せる。

contrast はノード種別にしない。 同一 problem 配下の複数 theory を比較する ビュー / 操作 / 派生オブジェクトとして扱う。

不採用

gap_contrast のような混成ノード。 何が theory の欠陥で、何が理論間比較なのかを失う。

明示的な contrast エッジを木構造のコアに入れる案も、現行実装と相性が悪い。 MVP では比較ビューの方が安全。

2. 背景: なぜ今の問題が起きるのか

概念の混線

Gap/Contrast には、理論の欠陥と理論間比較の2機能が混在している。

構造の不一致

gap は1理論にぶら下がるが、contrast は2理論以上をまたぐ。単一ノードにしにくい。

UIの曖昧さ

ユーザーは「不足点を書く」のか「他説との違いを書く」のかで迷う。AIもコメント先を決めにくい。

3. 推奨する情報モデル

ノード種別 役割 典型的な問い 許可する子
problem 説明したい問い・不明点・タスク 何がまだ分からないか working_theory, synthesis
working_theory 現時点の説明・仮説・解釈 いまどう説明するか mismatch, evidence, working_theory
mismatch この理論では説明できない点 何が合わないか / 何が抜けているか evidence, working_theory
evidence 根拠、実行結果、資料、教師説明 何がこの理論を支えるか / 退けるか なし
synthesis rise-above した改善説明 今の共同体説明は何か なし

ポイント

contrast はここにいない。contrast は 同一 problem 配下の複数 working_theory を比較する UI 操作で表現する。 つまり node kind ではなく relation/view として持つ。

4. 木構造としての最小表現

problem: なぜこのループは最後の要素を処理しないのか
  working_theory: i < arr.length - 1 だから最後が飛ぶ
    mismatch: empty array のときの挙動をまだ説明していない
      evidence: 実行トレースで i の値と条件式を確認
      working_theory: 境界条件だけでなく初期化条件も影響している
    evidence: 条件式の真偽を各反復で記録
  working_theory: break 条件が先に発火している
    evidence: 途中の return / break を確認
  synthesis: 原因は境界条件の設定と break 条件の組み合わせ

同じ problem の下に複数の working_theory を置けるので、alternative theory は専用 kind なしでも表現できる。

5. Contrast をどう扱うか

設計原理

  • contrast は最低2つの theory があって初めて成立する。
  • 比較対象は sibling theory、改訂前後の theory、theory と canonical explanation のいずれか。
  • 木の中に無理に埋めるより、選択ビューで並置した方が認知負荷が低い。

MVP の実装形

  • Problem を選ぶと、その直下の theory を横並びで比較表示する。
  • 比較ビューでは「一致点」「相違点」「判別に必要な evidence」を出す。
  • 保存は必須にしない。最初は派生表示でよい。

避けるべきこと

contrast を単一ノードにすると、 「A理論とB理論の違い」なのか「A理論の欠点」なのかが崩れる。 これは作成者にも閲覧者にも不親切で、AIコメントも不安定になる。

6. ユーザーフロー

1

Problem 作成

説明したい問いやコード片に対する疑問を立てる。

2

Theory 追加

1つ以上の working theory を追加する。

3

Mismatch 追加

各 theory の不足点や矛盾点を書き出す。

4

Compare

Problem 直下の theory を比較して差異を可視化する。

5

Evidence 追加

資料や実行結果でどの theory が妥当かを絞る。

6

Synthesis 作成

改良説明または共同体の暫定合意を残す。

7. AI 支援の置き場所

Problem 向け

  • 問いの粒度を整える
  • 前提条件の不足を指摘する
  • 比較すべき対象を提案する

Working Theory / Mismatch 向け

  • 抜けている状態変化を指摘する
  • 説明していないコード行を示す
  • 矛盾しうるケースを挙げる

Contrast / Compare 向け

  • 一致点と相違点を要約する
  • 判別に必要な evidence を提案する
  • 確信度つきで比較結果を返す

ガードレール

AI は「これが正解」と閉じる役ではなく、 不足点・比較観点・確認すべき evidence を出す役に寄せる。 near-correct explanation への誤検出があるため、断定より候補提示が基本。

8. 現行コードベースへの落とし込み

対象 現状 設計変更

src/pages/admin-page.tsx CTA 管理画面 schema ごとの説明文と root 作成UIを切り替える。

MVP で守ること

比較を保存可能なグラフ構造にしなくてもよい。 まずは 木構造のまま theory を複数持てるようにし、compare view を派生表示にする。 これならデータモデルの破壊が小さい。

9. 推奨する実装フェーズ

  1. schema registry 化。CTA schema と inquiry schema を並立させる。
  2. inquiry schema で problem / working_theory / mismatch / evidence / synthesis を追加する。
  3. Problem 選択時の compare view を入れる。最初は非保存でよい。
  4. AI で mismatch 候補と compare summary を生成する。confidence と根拠必須。
  5. 必要なら compare 結果を保存オブジェクト化する。
